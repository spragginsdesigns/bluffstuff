FIXED: theme toggle did DOM work inside a setState updater

Fixed

ThemeProvider.tsx called classList.toggle, localStorage.setItem, and a meta-tag write inside the updater passed to setThemeState. React requires updaters to be pure and may re-invoke them when a render is retried or discarded, which is common on this page because Clerk and Convex push updates constantly. A second invocation flips the class back: the click does nothing, and state drifts out of sync with the DOM. That is the "have to click it multiple times" behavior.

Evidence: before and after
// BEFORE — side effects inside the updater (impure)
const toggle = useCallback(() => {
  setThemeState((current) => {
    const next = current === "dark" ? "light" : "dark";
    document.documentElement.classList.toggle("dark", next === "dark"); // can run twice
    localStorage.setItem(THEME_STORAGE_KEY, next);
    return next;
  });
}, []);

// AFTER — side effects run once, in the event handler
const applyTheme = useCallback((next: Theme) => {
  document.documentElement.classList.toggle("dark", next === "dark");
  try { localStorage.setItem(THEME_STORAGE_KEY, next); } catch {}
  document.querySelectorAll('meta[name="theme-color"]')
    .forEach((el) => el.setAttribute("content", THEME_COLORS[next]));
}, []);
const setTheme = useCallback((next: Theme) => {
  applyTheme(next);
  setThemeState(next);
}, [applyTheme]);
const toggle = useCallback(() => {
  setTheme(theme === "dark" ? "light" : "dark");
}, [theme, setTheme]);

ThemeToggle also gained aria-pressed and a state-aware label ("Switch to light/dark mode") so screen readers announce what the button will do.

next@14.2.6 carries a published security vulnerability

High

RSVP form never actually auto-fills for signed-in residents

Medium

RsvpModal.tsx:39-42 seeds name and email with useState(user?.fullName ?? ""). Clerk's useUser() is still loading on first render, so the initial state is empty and never updates when the user arrives. Fix: a small useEffect that fills the fields once user resolves, only while the fields are still untouched.

"No upcoming events" flashes while events are still loading

Medium

page.tsx:25 coerces the loading state with upcomingEventsRaw ?? [], so every visitor on a slow connection first sees the empty state, then the events pop in. The IdeaBoard already does this correctly with a spinner on undefined; reuse that pattern for the events grid and the hero's next-event card.

Failed online payments fail silently

Medium

EventCard.tsx:51-53 catches a failed /api/checkout call and only resets the spinner. A resident whose payment cannot start sees the button return to "Pay Online" with no explanation. Show the caught error message in the card, the same way RsvpModal shows its error state.

Calendar day taps drop events and only scroll

Low

A day with several events fires onEventClick(dayEvents[0]) and the handler merely scrolls to the events section, so tapping a day never shows which event it holds and extra events are invisible. Either open the tapped event's detail directly, or list that day's events in the month panel. Past months also always read "No events scheduled" because only upcoming events are passed in.

The whole homepage is one client component

Low

page.tsx starts with "use client", so nothing on the page is server-rendered: first paint waits on the full JS bundle, and search engines see an empty shell. Moving the static sections (committee, FAQ, contact) into server components and keeping only the live islands (events, idea board) on the client would cut time-to-content on the phones most residents use.

Mobile tab bar gives no sense of place

Low

The five bottom tabs never highlight the section on screen. A scroll-spy active state (or at minimum aria-current on tap) would help residents orient on a long single-page layout.

What is already in good shape

Healthy

The design-token system is clean: every color pair is contrast-checked in both themes, the pre-paint init script prevents a theme flash, and the modal is a real <dialog> with focus containment and Escape handling. Touch targets are generous (44px+), forms have proper labels, and the idea board's loading and empty states are the model the events grid should copy.
